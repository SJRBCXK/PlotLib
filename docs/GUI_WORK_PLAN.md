## 2. 目标与范围

把数据前处理（现有的两个 Qt 工具）、编组、绘图、导出整合进一个桌面程序。

一句话概括：**GUI 是帮用户写脚本的界面。** 用户点按钮、选下拉框，就是在一点一点填下面这几行的参数：

```python
dataset = Dataloader(...).load_data(path)     # 读数据
groups  = Group(dataset, {...})               # 定分组
plotter = DataPlotter(dataset, groups, ...)   # 定外观
plotter.plot(Layer(0, 1), by='group')         # 画
```

## 3. 架构（2026-11-27 初步定稿）

```text
面板（Qt：按钮、下拉框、画布）  →  Session（纯 Python）  →  plotlib（不动）
        ▲                                │
        └──── 接线：Session 变了 → 读出状态、转成普通数据交给相关面板 ────┘
```

### 3.1 三块各管什么

| 块 | 管什么 | 不管什么 |
|---|---|---|
| 面板（`panels/`） | 让用户操作；按 Session 的当前状态显示 | 不保存数据和设置；面板之间不互相调用 |
| Session（`session.py`） | 保存数据集、分组、绘图设置、各次绘图的结果；把操作转成库的调用；失败回滚；变了就发通知 | 不导入 Qt；不做计算，配色、分图这类规则只在库的 `plan.py` 里 |
| plotlib | 读数、分组、生成计划、渲染 | 不知道 GUI 的存在 |

**为什么需要 Session**：库的接口是「一次说完」，`plot()` 要一次拿到全部参数；GUI 是「一点一点说」，参数来自不同控件、不同时间。
总要有个地方把它们攒起来。放在主窗口上也能做，但几个面板共用同一份数据时会互相牵扯，而且要开窗口才能测试；
Session 就是把这些属性和「点绘图时做的事」单独拿出来，可以像库一样用 pytest 测试。

主窗口负责接线：把 Session 的通知接到面板的刷新上。之前设想的单独 controller 层取消，不需要再多一层。

### 3.2 两条规矩

1. **读直接读，改走 Session。** 接线层可以直接读 Session 持有的库对象（如 `session.groups.sample_ids(name)`、`session.dataset.names`），
   这些读接口本来就返回副本；读出来转成普通数据再交给面板（面板是被动视图，不认识 Session，见 3.5）。
   凡是改变状态的操作都经过 Session，因为只有经过它才能失败回滚、通知其他面板。
2. **不写只转发的方法。** Session 的每个方法都要做库不管的事（把参数凑齐、回滚、关旧图、发通知）。
   只是原样转发的方法（如 `group_names()` 直接返回 `self.groups.names`）不写，否则就成了《重构》里的「中间人」坏味道。

这种分法就是常见的 MVC / MVP / MVVM，Session 相当于 Model（或 ViewModel）。

### 3.3 原则（与内核原则的对应）

| GUI 原则 | 做法 | 内核里的同款 |
|---|---|---|
| 东西只存一份 | 分组只存在 Session 的 `Group` 里，面板每次显示时现读，不另存一份列表 | 3.1：`Group` 是分组的唯一主人 |
| 规则只写一次 | GUI 不写「什么组合合法」的判断，库报 `ValueError` / `TypeError`，GUI 接住并显示；控件变灰只是提示，不算判断 | 原则 2、5、11：规则只在 `plan.py`，尽早报错 |
| 失败不留半成品 | 先在旁边把新图画好，全部成功才生效；失败时已有的图和上一份有效设置都不变，状态栏显示错误 | 原则 12；`_render` 全部成功才替换 `figures` |
| 数据单向流动 | 操作 → Session 改状态 → 通知 → 接线层现读、交给面板刷新；面板刷新控件时临时屏蔽信号，避免循环 | 原则 6：回调顺序固定 |
| 设置是纯数据 | 绘图设置是冻结的 `PlotRequest`，字段由库现成的 `Layer`、`LineStyle`、`FrameStyle` 等组成，不另造样式字段；选项用标准写法（`'dash'` 不是 `'--'`） | `FigureSpec` 约定；3.2 标准写法；冻结的样式对象 |
| 现建不缓存 | 每次绘图按当前状态新建 `DataPlotter`，不长期持有 | 原则 13 |
| 借了要还 | 图从 Session 里移除时（被替换或被用户删除）对它调用 `backend.close`；matplotlib 后端用 `plt.subplots` 建图，不关会一直攒在 pyplot 里 | `_render` 失败时关已画好的图 |
| 预览与导出分开 | 预览主题（浅底、高亮当前曲线）是 GUI 自己的 matplotlib `figure_formatter`；高亮、翻页只操作已有的 `DrawnFigure`（`artist(样品号)`），不重新生成计划；导出时不带预览主题重画 | 原则 3：滑块是画完之后的交互；原则 4：原生回调不跨后端 |
| 先看值不值得做 | 第一版同步绘图、不开线程、不做撤销和工程文件，只保证设置能序列化 | 第 2 节补充原则的前提 |

### 3.4 外观与结构的边界

另一个 Agent 改 qss 和面板内布局，这边改数据流，互不影响。两边只约定三样：

- 面板的 objectName 和 `role` 属性（现在骨架里 `make_panel` 和 `setProperty("role", "section")` 的写法）；
- Session 的方法和通知；
- 面板对外只有两类接口：发出操作、显示接线层给它的数据（被动视图，见 3.5）。

对应内核里 `layouts.py`（长什么样）和 backend（怎么画）的分工。

### 3.5 与前端 Agent 的约定（2026-11-27）

用户定：界面的全部绘制（主窗口、面板、子窗口外框、样式表、字体）都交给前端 Agent。这边只写 Session 和接线。

**目录**（G2 已建好 `__main__.py`、`main_window.py`、`theme/`；`session.py`、`panels/` 到 G4、G5 再建）：

```text
src/plotlib_gui/
    __main__.py        启动：建 Session 和主窗口，把两边接起来（这边写）
    session.py         Session（这边写，不导入 Qt）
    main_window.py     主窗口（前端写）
    panels/            各面板（前端写）
    theme/             plotlib.qss、chevron-down.xpm、qt_theme.py、preview_theme.py、fonts/（前端写）
docs/GUI_DESIGN_PROMPT.txt   前端的设计说明
```

导入一律写绝对路径（`from plotlib_gui.theme.qt_theme import ...`），不再用 `if __package__` 分支。
`theme/fonts/` 是本机自备的字体，不进 git、不随包安装；新加的 qss、图标等非 .py 文件要在 `pyproject.toml` 的 package-data 里登记。

**面板是被动视图，只做两件事**（11-27 修订，为了让前端能和 Session 并行开发）：

- **发出操作**：用户的操作通过 Qt 信号发出去，参数是普通的 Python 数据（字符串、数字、列表、字典），比如「要打开这个文件」「要按分组画」，面板自己不去执行；
- **显示给它的数据**：提供 `set_xxx(普通数据)` 方法，接线层从 Session 读出状态（读直接读 `session.dataset`、`session.groups`），转成普通数据后交给面板；
  面板刷新控件时屏蔽信号。表单类面板统一提供 `values()`、`set_values()` 和 `changed` 信号。

面板不导入 Session，也不调用 plotlib；唯一的例外是可以读 `plotlib.style` 里的选项表（如 `LINESTYLES` 的键），把它们当下拉框的选项，这是只读数据，
这样标准写法只有一份。面板里不写数据处理和判断规则，面板之间不互相引用。每个面板都能用假数据单独运行。
组件清单和暂定的信号、方法名见 `GUI_COMPONENTS.md`，最终名字在 G5 接线时双方一起定。

**主区域**：右侧绘图区改成 `QMdiArea`（决定 4），每张图一个子窗口。子窗口的外框样式归前端，窗口里放的画布（`FigureCanvasQTAgg` 或 `QWebEngineView`）由接线层放进去。

**左侧目录**：

- 「数据集 / 组 / 图形」三个页签都是目录；绘图设置不在左栏，从「绘图」菜单打开设置窗口（11-27 按前端反馈改）；
- 「数据集」页列出所有数据集（树形，显示子数据集的来源），「组」页显示选中数据集上的分组（用户 11-27 确认）：分组属于数据集，和库里 `Group` 必须建在同一个数据集上一致；
  选中哪个数据集是界面状态；
- 「图形」页是**绘图结果目录**，按「绘图批次 → 图形」列出结果（决定 4a）。单击选中，双击或回车打开或激活对应的窗口。

### 3.6 性能实测（2026-11-27）

18 个样品、9 个分组、每样品 5 万行，各项取 3 次中最快的一次：

| 环节 | 耗时 |
|---|---|
| 新建 `DataPlotter` | 0.02 ms |
| 只生成计划 `plan_figures` | 0.06 ms |
| `plot()` 建图对象：`by='all'` 1 张 / `'group'` 9 张 / `'sample'` 18 张 | 35 / 65 / 94 ms |
| 显示一张图（`canvas.draw` 栅格化） | 66～477 ms（18 条 × 5 万点画在一张图上最慢） |

结论：Session 这一层的开销可以忽略；真正的开销是 matplotlib 栅格化，与点数 × 线数成正比，脚本用 `plt.show()` 也要付。
只为显示出来的图栅格化。实测中没有关旧图时 matplotlib 立刻警告打开超过 20 张图，这证实了「借了要还」必须做。

内存（100 张图、每张 1 条线、1200 × 800 像素，Windows 工作集）：

| 每样品行数 | 只建对象（不显示） | 栅格化后每张再加 |
|---|---|---|
| 2000 | 约 0.4 MB / 张 | 约 5.6 MB / 张 |
| 50000 | 约 2.5 MB / 张 | 约 6.5 MB / 张 |

占内存的主要是显示用的像素缓冲，不是图本身。所以窗口数要设上限，结果里的图数不用设（决定 4）。

慢了以后的手段（现在都不做，按代价从小到大）：手动点「绘图」才重画；大数据只在预览时降采样；后台线程渲染（pyplot 不是线程安全的，最后才考虑）。

**参照**：Origin 把内容放在工程文件（.opju）里，窗口只负责显示；对话框背后对应 X-Function / LabTalk 命令；分析结果有 None / Auto / Manual
三种重算模式。matplotlib 自己的 `Figure` 与 `FigureCanvas`、Qt 的 Model/View 也是同一种分法。

### 5.0 先认识几个概念

用户提到的「运行态、暂存态、动作态」，在软件设计里有对应的常见说法。先把 GUI 里会出现的「东西」按性质分一下类：

| 类别 | 常见说法 | 在我们这里是什么 | 放在哪里 |
|---|---|---|---|
| 已生效的状态（用户说的「运行态」） | 状态（state）、模型（model） | 数据集、分组、各批绘图结果 | Session |
| 还没生效的修改（「暂存态」） | 草稿（draft）、待提交（pending） | 设置面板里改了、还没点「绘图」的设置；分组对话框里还没点「确定」的内容 | 待定（G4.1） |
| 一次操作（「动作态」） | 动作（action）、命令（command）、意图（intent） | 「打开这个文件」「加一个分组」「按这些设置画」 | 面板发出，Session 执行 |
| 能从状态算出来的 | 派生数据（derived） | 目录里列出的图、样品表的显示内容、某个按钮该不该变灰 | 不存，用的时候现算 |
| 只跟界面有关的 | 界面状态（UI state、view state） | 当前选中哪个页签、开了哪些窗口、窗口队列（决定 4b）、窗口位置 | Qt 这边，不进 Session |
| 正在进行中 | 瞬态（transient） | 「正在绘图」时的忙碌光标 | 接线层，用完即消失 |

判断一个东西放哪里，问两个问题：**存工程文件（.plb）时要不要存它？** 要存的是状态，放 Session；
**换一个界面（比如以后做网页版）它还在不在？** 不在的是界面状态，留在 Qt。
对应内核：`DataSet`、`Group` 是状态；`FigureSpec` 是从状态算出来的派生数据（计划每次现算，不缓存）；`DrawnFigure` 是结果。

### G4.1 状态分类（讨论，不写代码）

**讲。** 先把「什么东西放哪里」定清楚，后面的代码只是照着写。分错了的典型后果：界面状态进了 Session，Session 就离不开 Qt；
派生数据被存了一份，就会和源头不一致（「东西只存一份」）。

**读 + 用户练习。**

1. 打开 `scripts/piezo.py` 的 `main()`，逐行标出每个变量属于上表哪一类（提示：`dataset`、`groups` 是状态，`plotter` 是什么？）；
2. 看 `GUI_COMPONENTS.md` 里每个组件显示的内容，标出它显示的是状态、派生数据还是界面状态；
3. 想一想：一批绘图结果里，除了画好的图，还要存什么，才能做到「以后按同样的设置再画一次」和「存进工程文件」？

**定。**

| # | 要定的事 | 建议 |
|---|---|---|
| 1 | 绘图设置的草稿放哪里 | 两种做法，组件接口都一样，只差接线层听不听表单的 `changed`（前端反馈第二轮第 3 条）。甲（前端建议）：窗口里的编辑留在窗口本地，点「绘制」时一次提交，Session 只存「上次提交的设置」，重开窗口时回填它；乙：每次改动都通过 `changed` 写进 Session 的草稿，重开时回填草稿。想一想：两种做法下，「绘制」失败了、或者改到一半关掉窗口，用户再打开看到的分别是什么？存工程文件时存的是哪一份？ |
| 2 | 对话框里没点「确定」的内容放哪里 | 放对话框自己：点「确定」才变成一个动作交给 Session，点「取消」什么都不发生，Session 从来不知道 |
| 3 | 一批结果存什么 | 设置（当时的 `PlotRequest`）+ 画好的图 + 用的后端 + 编号和时间；有了设置，才能重画和存工程 |
| 4 | 窗口队列放哪里 | 界面状态，放主窗口这边，不进 Session |
| 5 | 旧批次怎么按「当时」的数据重画（前端反馈第 6 条） | 留给用户在练习 3 之后定。提示：画完 A 以后，用户可能改分组（`Group` 是原地修改的）或导入新数据；导出 A 时要用的是画 A 时的数据和分组。两条思路：一批结果存一份数据集和分组的快照；或者规定 Session 从不原地修改这两个对象，每次修改都换成新对象，旧批次自然还拿着旧的 |
| 6 | 允许几个数据集同时存在（前端反馈第 2 条） | ✅ 11-27 用户定：**支持多数据集**。理由：处理数据会产生子数据集（`select` 选样品、`DataTransformer` 归一化、`Group.apply` 分组计算），样品和通道都和原数据不同，原数据上的分组也不能直接用，只能作为独立的数据集共存。这和 Origin 的多个工作簿、分析结果放进新表是同一种做法。由此带来的结构（G4.2 细化）：Session 存一组数据集条目，每条 = 编号 + 名字 + `DataSet` + 它自己的 `Group` + 来源（导入的文件，或由哪个数据集经什么处理得到）；
编号由 Session 分配，从 1 起只增不减，删除后也不再使用（和前端约定，`GUI_COMPONENTS.md` 第 1 节），这样窗口、旧批次里记着的编号永远不会指到别的数据集上；绘图设置要写明画哪个数据集；一批结果记下它画的是哪个数据集；选中哪个数据集是界面状态。约束：一次绘图只用一个数据集（`DataPlotter` 只收一个数据集；不同数据集的列混在一起时样品号怎么对应，内核计划第 6 节记为未定），要把两个数据集画在一张图上，得先用处理步骤合成一个新数据集 |

### G4.2 Session 的骨架和 `PlotRequest`（用户编写初版）

**讲。** `PlotRequest` 是「绘图设置」这份草稿的样子：一个冻结的 dataclass，字段对应 `DataPlotter(...)` 和 `plot(...)` / `plot_bars(...)` 的参数，
由库现成的冻结对象组成（`Layer`、`LineStyle`、`FrameStyle`、`LegendStyle`、`TickStyle`、`ColorbarStyle`、`BarStyle`、`AxisStyle`）。
改设置写成 `replace(request, by='group')`，得到一份新的设置，旧的不变。

再加一个**纯函数**，把 `PlotRequest` 翻译成库调用要的参数。它和内核的 `style.py` 是同一个角色：一边是界面上的写法，一边是库的写法，中间一层翻译，
可以不开窗口直接测试。

**读 + 用户练习。**

1. 读 `plotter.py` 里 `DataPlotter.__init__`、`plot`、`plot_bars` 的参数表，列出 GUI 要让用户能改的参数，每个参数写出它在界面上是什么控件；
2. 找出不能直接放进设置的参数：回调（`formatters`、`figure_formatter`）是函数，存不进 JSON。想一想怎么办（提示：`make_axes_formatter(x=AxisStyle(...))`）；
3. 用户写 `PlotRequest` 的初版和 `Session` 的字段。

**定。**

| # | 要定的事 | 建议 |
|---|---|---|
| 1 | 曲线图和柱状图的设置是一个类还是两个 | 两个（`CurveRequest`、`BarRequest`），对应 `DataPlotter` 构造参数的外观部分（字体、线条、边框、图例、刻度、尺寸）单独一个类、两者共用，名字避开库里已有的 `Appearance`；同内核 4.3「spec 按画法拆开」 |
| 2 | 回调怎么存 | 只存样式对象（`AxisStyle` 等标准写法），绘图时才用 `make_axes_formatter` 生成回调；GUI 不支持用户写任意回调 |
| 3 | 翻译函数叫什么、放哪里 | `session.py` 里的 `build_plotter(dataset, groups, request)`，返回画好图的 `DataPlotter`；纯函数，不碰 Session 的字段 |
| 4 | 翻译时按字段处理的细节（前端反馈） | `None` 的含义按字段来（`GUI_COMPONENTS.md` 第 1 节的表），不统一转换；颜色条设置只在至少一个图层有颜色映射时才传给库（没有映射时传 `colorbar` 库会报错），草稿里的颜色条设置照样保留 |

**测。** 翻译函数：给几份设置，检查画出的图数、图层、样式和直接写脚本调用库的结果一致（「GUI 是帮用户写脚本的界面」，那就拿脚本对照）。

### G4.3 通信：Session 怎么告诉界面「我变了」（观察者模式）

**讲。** 界面 → Session 是普通的方法调用。反过来，Session 不认识界面，不能去调用面板，只能说一句「我变了」，谁关心谁来听。
这叫**观察者模式**：Session 存一个回调列表，变了就逐个调用。Qt 的信号和槽就是同一个东西的 Qt 版本；Session 不导入 Qt，所以用普通回调，
接线层把它转给面板。内核里的同款是回调约定（原则 6）：接收对象、原地修改、顺序固定。

**读 + 用户练习。** 读 `learning/gui/step3_signals.py`，用自己的话说清楚信号、槽、`connect` 各是什么；再用十行纯 Python 写一个最小的观察者（一个类，能登记回调、能通知）。

**定。**

| # | 要定的事 | 建议 |
|---|---|---|
| 1 | 通知分多细 | 按状态的部分分几个话题：`'dataset'`（含分组）、`'request'`、`'results'`；接线层按话题决定刷新哪些面板。全部只用一个「变了」最简单，但每次都要刷新全部面板 |
| 2 | 什么时候通知 | 只在状态真的改成功之后；失败不通知 |
| 3 | 出错怎么告诉界面 | Session 不吞异常，原样抛给调用它的接线层，接线层显示在状态栏；Session 不需要专门的「出错」通知 |

**测。** 一条测试，循环几种操作：成功时状态先变、再通知，通知的话题对；失败时状态不变、不通知、异常原样抛出。

### G4.4 动作：「先算好、再提交、再通知」

**讲。** 每个改状态的方法都按同一个顺序：先在局部把新状态算好（库会在这一步校验、报错），全部成功才替换 Session 里的字段，最后通知。
这就是「失败不留半成品」（内核原则 12）在 Session 里的写法；`Group.add` 先校验全部再改、`_render` 全部画完才替换 `figures`，都是这个顺序。

第一版的动作：

| 动作 | 做什么 | 要注意 |
|---|---|---|
| `load(path, columns_per_sample)` | 读数据，**新增**一个数据集条目（多数据集，G4.1 第 6 项），分组为空 | `Dataloader` 取消选择会抛 `NoFileSelected` |
| `rename_dataset` / `delete_dataset` | 改名、删除数据集条目 | 删除被子数据集或绘图结果引用的数据集怎么办，G4.4 再定 |
| `add_group` / `edit_group` / `delete_group` | 调用某个数据集的 `Group` 的修改接口 | 编辑时组名不变；编辑器只给出用户动过的字段，在原配置的**副本**上应用：非空值覆盖，`None` **删除这个键**（`Group.set` 收到 `color=None` 会报错，省略才是恢复默认），再整份交给 `Group.set`，编辑器不认识的字段原样保留 |
| `update_request(...)` | 改设置草稿 | 草稿可以暂时不合法（比如还没选分组就选了按分组），点「绘图」时才由库报错 |
| `plot()` | 按草稿画，追加一批结果（决定 4a） | 失败时结果列表不变 |
| `delete_batch(id)` | 删一批结果 | 接线层先关掉这批的窗口；Session 再对其中每张图调用 `backend.close`（借了要还） |

**读 + 用户练习。** 用户写 `plot()` 的初版：调用 G4.2 的翻译函数，成功后追加一批，最后通知。写完对照上面的顺序自查。

**定。**

| # | 要定的事 | 建议 |
|---|---|---|
| 1 | 动作写成方法还是命令对象（「动作态」要不要成为对象） | 第一版写成方法。命令对象（每个操作是一个对象，Session 只有一个 `apply(动作)` 入口）的好处是能记录、撤销、回放，正好能做「导出成脚本」；等做撤销或导出脚本时再改，那时是机械改动 |
| 2 | 决定 8：换数据集时分组怎么办 | 见第 4 节，建议重建，失败则整个替换不生效 |
| 3 | 草稿合不合法谁来判断 | 不判断，交给库在绘图时报错（「规则只写一次」） |

**测。** 每类动作一条测试，场景在测试里循环：成功、失败（状态不变）、删除批次后图被关掉（pyplot 里的图数回到原来）；
编辑分组时没动过的字段原样保留。另加一条验收（前端反馈第 6 条）：画 A → 改分组或导入 B → 导出 A，核对 A 的数据、组成员和图数还是画 A 时的。

### G4.5 接线：被动视图和主窗口（与前端会合）

**讲。** 前端画好的面板只会发信号和显示普通数据（被动视图，3.5）。接线层在 `__main__.py` 里做三件事：
面板的信号 → 调用 Session 的方法（出错时显示在状态栏）；Session 的通知 → 从 Session 读出状态、转成普通数据交给面板；
结果的图 → 放进 MDI 子窗口（G3 的实验成果）。

**读 + 用户练习。** 用户挑一个面板（建议数据集页），自己写它的接线；其余面板由执行者照着写。

**定。** 信号、方法的最终名字（`GUI_COMPONENTS.md` 里是暂定的）；面板刷新时屏蔽信号的写法（`QSignalBlocker`）。

**测。** offscreen 冒烟测试一条：建主窗口和 Session，打开一个小数据文件、加一个分组、画一批，检查目录里出现了结果、开了窗口。
再加一条（前端提出）：数据集 A、B 都有样品 0 和分组「对照组」，打开 A 的分组编辑器后在目录里切到 B，点确定，修改仍作用于 A、B 不变。
